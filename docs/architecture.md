# Архитектура проекта HAL_I2C

> Учебный проект. Цель — не готовое устройство, а разобраться с I2C на STM32 HAL:
> протокол, DMA, восстановление зависшей шины, критические секции между main-циклом
> и прерываниями. Решения ниже адекватны учебным задачам и **не рассчитаны** на
> продакшн без ревизии (см. «Известные ограничения»).

## Что делает прошивка

Раз в секунду опрашивает BME280 (температура/давление/влажность), пишет
температуру в AT24C02 (I2C EEPROM), читает её обратно и сверяет с исходной —
это одновременно тест EEPROM-драйвера и тест самого I2C-стека под реальным
round-trip. Результат и ошибки идут в лог по SWO (`printf` → ITM → SWO), без UART.

## Аппаратная платформа

| | |
|---|---|
| MCU | STM32F411CEUx (Cortex-M4, 100 МГц) |
| Шина | I2C1 (PB6 = SCL, PB7 = SDA), 100 кГц, DMA |
| Датчик | BME280, адрес `0x76` |
| Память | AT24C02 (EEPROM, 256 байт), адрес `0x50` |
| Вспомогательно | TIM10 — источник задержек в микросекундах для bus recovery |
| Индикация | светодиод на PC13, включается в `Error_Handler` |
| Отладочный вывод | SWO/ITM (`_write` → `ITM_SendChar`) |

## Слои

```
┌─────────────────────────────────────────────┐
│ main.c                                       │  инициализация, главный цикл,
│                                               │  Error_Handler, конфигурация пинов
├───────────────────┬───────────────────────────┤
│ BME280.c/h         │ AT24C02.c/h               │  драйверы устройств:
│ (датчик)           │ (EEPROM)                  │  протокол устройства, компенсация,
│                     │                           │  own retry/round-trip логика
├───────────────────┴───────────────────────────┤
│ i2c_driver.c/h                                │  общий слой поверх HAL:
│                                               │  блокирующий API, bus recovery,
│                                               │  критические секции
├─────────────────────────────────────────────┤
│ STM32 HAL (HAL_I2C_*_DMA, HAL_GPIO_*, ...)   │
└─────────────────────────────────────────────┘
```

Правило слоёв: **драйвер устройства не знает про регистры I2C**, `i2c_driver`
не знает про BME280/AT24C02, `main.c` не лезет в HAL напрямую (кроме
инициализации, которая целиком сгенерирована CubeMX и живёт в `MX_*_Init`).

## Модули

| Файл | Отвечает за |
|---|---|
| `i2c_driver.c/h` | Транспорт: одна блокирующая передача за раз, повторы, восстановление зависшей шины, таймаут |
| `BME280.c/h`, `BME280_REG.h` | Инициализация датчика, чтение и компенсация T/P/H по формулам из даташита |
| `AT24C02.c/h` | Постраничная запись/чтение EEPROM с учётом границ страницы |
| `utils.c/h` | Форматированный вывод измерений в SWO |
| `led.h` | Индикация ошибки (макрос `ERROR_LED_ON()`) |
| `main.c/h`, `stm32f4xx_hal_msp.c`, `system_*` | Код CubeMX: тактирование, GPIO, DMA, NVIC — не редактируется вручную вне `USER CODE` |

## Ключевые решения и почему

**Блокирующий API вместо очереди задач.**
Первая версия `i2c_driver` умела ставить передачи в очередь и работать
асинхронно. От этого отказались: в проекте нет источника параллельных
запросов к шине (один датчик и одна память, опрашиваются последовательно
из одного цикла), а асинхронность добавляла сложность без выгоды —
каждый вызывающий код всё равно тут же ждал результата. Асинхронный
драйвер имеет смысл с RTOS, когда действительно есть несколько
независимых потребителей шины.

Итог — `i2c_transmit/receive/mem_write/mem_read` возвращаются только
когда обмен завершён, отброшен после `I2C_MAX_RETRIES` повторов или
истёк таймаут. Один активный дескриптор передачи на шину
(`i2c_bus_t.current`), не очередь.

**Критические секции через PRIMASK, а не запрет конкретного прерывания.**
Состояние шины (`i2c_bus_t.state`) меняют и главный цикл (постановка
новой передачи), и обработчики прерываний DMA/I2C (её завершение).
Классическая гонка «прочитать-и-записать» без защиты. Решение —
короткие критические секции (`__get_PRIMASK/__disable_irq/__set_PRIMASK`)
строго вокруг проверки-и-установки состояния, не вокруг вызовов HAL.
`__enable_irq()` намеренно не используется — он включает прерывания
безусловно и ломает вложенные критические секции; `__set_PRIMASK`
восстанавливает то, что было.

**Восстановление шины (bus recovery).**
Если ведомое устройство держит SDA прижатой к земле (зависло в середине
байта — например, после сброса мастера), шина не восстановится сама.
`i2c_bus_recovery()` вручную тактирует SCL до девяти раз, пока SDA не
отпустят, затем формирует STOP низкоуровневыми GPIO-операциями. Триггер —
`is_i2c_bus_stuck()` перед каждым повтором после ошибки.

**Пины шины не берутся из HAL.** `I2C_HandleTypeDef` не хранит, какие
GPIO использует шина (их конфигурирует пользовательская
`HAL_I2C_MspInit`, и это нигде не записывается) — а bus recovery
управляет линиями напрямую, в обход периферии I2C. Поэтому SCL/SDA/AF
вынесены в свой дескриптор `i2c_bus_t`, который явно описывается в
`main.c` рядом с `hi2c1`.

**DMA приёма — только `DMA_NORMAL`.** В циклическом режиме
(`DMA_CIRCULAR`) HAL не возвращает канал в `HAL_DMA_STATE_READY` после
одной передачи, и вторая же попытка чтения получает `HAL_BUSY`.
Грабля, наступить на которую легко, если копировать конфигурацию DMA
не глядя (CubeMX по умолчанию предлагает `CIRCULAR` для некоторых
периферий).

**Round-trip как способ проверить весь стек.** Запись температуры в
EEPROM и чтение её обратно — не столько нужная фича, сколько дешёвый
sanity-тест: если I2C-драйвер, DMA и протокол устройства работают
верно, записанное и прочитанное совпадут. Несовпадение проверяется
явно (`written != BME280_meas_data.temp`), а не полагается на то, что
глаза заметят разницу в логе.

## Обработка ошибок

Простая и однородная по всем модулям схема: у каждого потребителя шины
свой счётчик подряд идущих неудач (`static` в `*_process()`), при
превышении порога — `Error_Handler()` (мигание/свечение светодиода,
`__disable_irq()`, зависание навсегда). Ошибка транспорта отделена от
ошибки устройства: `i2c_driver` возвращает `I2C_TIMEOUT`/`I2C_ERROR_BUS`,
не зная, что за устройство на другом конце; `BME280`/`AT24C02` уже сами
решают, что делать с неудачей на своём уровне (повтор, диапазонная
проверка, round-trip).

Это не production-грейд обработка отказов (нет деградации, нет
восстановления без перезагрузки), но для одноплатного стенда с
физическим доступом к RESET — достаточно.

## Известные ограничения

Не баги, а осознанные границы учебного масштаба:

- **Одна передача на шину одновременно**, без очереди — до первого
  сценария, где обмен нужно инициировать из нескольких мест
  (например, из ISR и из main одновременно).
- **`i2c_driver` не потокобезопасен относительно нескольких вызывающих
  контекстов**, использующих одну и ту же шину параллельно (не путать
  с безопасностью относительно ISR завершения — она обеспечена). Под
  RTOS с несколькими задачами на одной шине понадобится мьютекс сверху.
- **Конфигурация BME280 (oversampling, фильтр, standby) зашита в
  `static const BME280_config`** на этапе компиляции — нет runtime API
  для её смены.
- **Нет модульных тестов.** Верификация — только запуском на железе и
  наблюдением по SWO.
- **`i2c_bus_recovery()` жёстко использует `GPIO_MODE_OUTPUT_OD` с
  внутренней подтяжкой** — на линиях без внешних резисторов подтяжки
  это единственная опора, но она слабее внешних 4.7 кОм, что может
  сказаться на скорости фронтов при более высоких частотах шины, чем
  100 кГц.
- **Восстановление после фатальной ошибки — только через RESET**
  (`Error_Handler` не возвращается).

## Структура каталогов

```
HAL_I2C/
├── Core/
│   ├── Inc/          заголовки: как сгенерированные CubeMX, так и свои
│   │                 (i2c_driver.h, BME280.h, AT24C02.h, utils.h, led.h)
│   └── Src/          соответствующие .c
├── Drivers/           STM32 HAL и CMSIS — не редактируется
├── docs/              этот документ
├── HAL_I2C.ioc        конфигурация CubeMX (источник истины для MX_*_Init)
└── CMakeLists.txt     сборка (сгенерирован CubeMX/CubeIDE)
```

## Сборка

CMake + `arm-none-eabi-gcc` (toolchain из STM32CubeCLT). Прошивка и SWO —
через ST-Link. Изменения в тактировании/пинах вносятся через CubeMX
(`HAL_I2C.ioc`) и перегенерацию, а не руками в `MX_*_Init` — иначе
следующая генерация их затрёт.

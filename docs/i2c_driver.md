# Заметка: драйвер `i2c_driver` / `timer`

Что сделано в блокирующем I2C-драйвере поверх STM32 HAL и почему именно так.

## Публичный API

```c
i2c_status_t i2c_bus_init(i2c_bus_t * bus);

i2c_status_t i2c_transmit  (i2c_bus_t * bus, uint8_t dev_addr, uint8_t * data, uint16_t len);
i2c_status_t i2c_receive   (i2c_bus_t * bus, uint8_t dev_addr, uint8_t * data, uint16_t len);
i2c_status_t i2c_mem_write (i2c_bus_t * bus, uint8_t dev_addr, uint8_t * data, uint16_t len, uint8_t mem_addr);
i2c_status_t i2c_mem_read  (i2c_bus_t * bus, uint8_t dev_addr, uint8_t * data, uint16_t len, uint8_t mem_addr);
```

Все четыре — **блокирующие**: возвращаются, когда обмен завершён, отброшен после
`I2C_MAX_RETRIES` повторов или истёк таймаут. Внутри — DMA, но снаружи это выглядит
как обычный синхронный вызов. `dev_addr` — уже сдвинутый 7-битный адрес (`0x76 << 1`),
это соглашение действует по всему API. Вызывать из обработчика прерывания нельзя —
внутри `HAL_GetTick()`-поллинг и потенциальный `printf`.

## Почему блокирующий API, а не очередь задач

Была версия с кольцевой очередью передач и асинхронным запуском. Отказались: в
проекте нет источника параллельных запросов к шине (один датчик и одна память,
опрашиваются последовательно из одного цикла) — очередь добавляла код
(голова/хвост, `retry_count` на каждую запись, отдельная синхронизация) без
единой реальной выгоды, потому что вызывающая сторона всё равно сразу же ждала
результата. Асинхронность имеет смысл под RTOS, когда действительно есть
несколько независимых потребителей шины — тогда это будет переписано заново
вокруг очереди FreeRTOS, а не подпёрто вручную.

Следствие: один активный дескриптор передачи на шину (`i2c_bus_t.current`), а
не массив.

## Дескриптор шины `i2c_bus_t` — зачем он, а не просто `I2C_HandleTypeDef *`

```c
typedef struct
{
    I2C_HandleTypeDef * hal;
    GPIO_TypeDef * scl_port;  uint16_t scl_pin;
    GPIO_TypeDef * sda_port;  uint16_t sda_pin;
    uint32_t gpio_af;
    TIM_HandleTypeDef * delay_tim;   /* 1 тик = 1 мкс, должен быть уже запущен */

    i2c_transfer_t        current;
    volatile i2c_state_t  state;
    volatile i2c_result_t last_result;
} i2c_bus_t;
```

`I2C_HandleTypeDef` **не хранит номера пинов SCL/SDA** — их конфигурирует
пользовательская `HAL_I2C_MspInit`, и эта информация нигде не сохраняется.
А bus recovery (ниже) должно управлять этими линиями напрямую через GPIO, в
обход периферии I2C — значит, пины нужно нести отдельно. Отсюда и
`delay_tim`: recovery тактует SCL вручную, микросекундными паузами, и
единственный доступный источник точного времени — свободно бегущий таймер
(`TIM10`, prescaler даёт 1 тик = 1 мкс), а не `HAL_Delay` (миллисекундная
дискретность, слишком грубо для 5 мкс).

Регистрация шины (`i2c_bus_init`) кладёт указатель на неё в статический
реестр `i2c_buses[I2C_MAX_BUSES]`. Реестр нужен исключительно колбэкам HAL —
они получают `I2C_HandleTypeDef *`, а всё состояние живёт в `i2c_bus_t`,
`i2c_bus_by_handle()` находит нужный дескриптор по `hal`-указателю.

## Жизненный цикл одной передачи

```
i2c_transmit/receive/mem_write/mem_read
        │
        ▼
   i2c_run()              заполняет bus->current, сбрасывает last_result,
        │                 вызывает i2c_try_start()
        ▼
 i2c_try_start()           критическая секция: state IDLE → BUSY,
        │                 затем HAL_I2C_..._DMA(). Ошибка запуска → state = ERROR
        ▼
 i2c_wait_ready()          крутится, пока не истечёт таймаут:
        │                 - HAL завершил DMA → колбэк ставит state = IDLE
        │                 - ошибка на шине → колбэк ставит state = ERROR,
        │                   i2c_error_process() внутри цикла разбирает её
        ▼
   результат: I2C_OK / I2C_TIMEOUT / I2C_ERROR_BUS
```

Колбэки `HAL_I2C_Master/MemTx/RxCpltCallback` и `HAL_I2C_ErrorCallback` —
единственное, что выполняется в контексте прерывания. Они трогают только
`bus->state` (это поле и помечено `volatile`). Поле `bus->current` из ISR
не трогает никто — значит, ему `volatile` не нужен: квалификатор нужен
там, где переменную видят два асинхронных контекста, а не по умолчанию
всему, что рядом с прерыванием.

## Критические секции — зачем `PRIMASK`, а не `__enable_irq()`

Проверка-и-установка состояния (`state != IDLE → return; иначе state = BUSY`)
в `i2c_try_start()` — не атомарная пара сама по себе: между проверкой и
записью может вклиниться прерывание. Решение — короткая критическая секция
строго вокруг этой пары, не вокруг вызова HAL:

```c
uint32_t primask = __get_PRIMASK();
__disable_irq();
if (bus->state != I2C_IDLE) { __set_PRIMASK(primask); return; }
bus->state = I2C_BUSY;
__set_PRIMASK(primask);
```

`__set_PRIMASK(primask)` восстанавливает то, что было, а не включает
прерывания безусловно. `__enable_irq()` сделал бы именно это — и сломал бы
вложенные критические секции: если вызывающий код уже запретил прерывания
сам, наш `__enable_irq()` разрешил бы их посреди чужой защищённой секции.

## Восстановление шины (bus recovery)

Триггер — `is_i2c_bus_stuck()`: если ведомое устройство держит SDA прижатой
к земле (типичная причина — сброс мастера посреди байта), шина сама себя не
восстановит. `i2c_bus_recovery()`:

1. `HAL_I2C_DeInit` + перевод SCL/SDA в open-drain с подтяжкой.
2. До девяти тактов SCL, пока SDA не отпустят (девять — с запасом на
   9-битный кадр I2C, худший случай).
3. Ручной STOP через GPIO: **SCL вниз → SDA вниз → SCL вверх → SDA вверх**.
   Порядок принципиален — опустить SDA при уже высоком SCL означало бы
   сформировать START, а не STOP.
4. Возврат пинов в `GPIO_AF_OD` и `HAL_I2C_Init`.

Вызывается из `i2c_error_process()` перед очередным повтором, но только
если `is_i2c_bus_stuck()` подтвердила зависание — на обычный NACK/таймаут
без физического зависания линии recovery не тратится.

## Таймаут и повторы

```c
timeout = len + I2C_TIMEOUT_BASE_MS;              /* мс */
while ((HAL_GetTick() - start) < timeout) { ... }
```
Разность тиков, а не `start + timeout` — `uwTick` переполняется примерно
через 49 суток, беззнаковая разность это переживает, сравнение с суммой —
нет.

Два разных исхода отказа различаются через `i2c_bus_t.last_result`:
- **`I2C_RESULT_FAIL`** — `i2c_error_process()` исчерпала `I2C_MAX_RETRIES`
  повторов и сдалась. Устройство реально не отвечает.
- **`I2C_WAIT_TIMEOUT`** — цикл ожидания в `i2c_wait_ready()` не дождался
  завершения за отведённое время (шина зависла настолько, что даже HAL не
  сообщил об ошибке). В этой ветке `HAL_I2C_DeInit`+`HAL_I2C_Init`
  обязательны — иначе DMA продолжит писать в буфер вызывающего уже после
  его возврата из функции.

Порядок проверок в `i2c_wait_ready()` важен: после исчерпания повторов
`state` тоже становится `I2C_IDLE` (как при успехе), поэтому проверка
`last_result == I2C_RESULT_FAIL` идёт **раньше** проверки `state == I2C_IDLE`
— иначе отказ выглядел бы как успех.

## Известные грабли, на которые уже наступали

- **DMA приёма обязан быть `DMA_NORMAL`, не `DMA_CIRCULAR`.** В циклическом
  режиме HAL не возвращает канал в `HAL_DMA_STATE_READY` после одной
  передачи — вторая же попытка чтения получает `HAL_BUSY`. CubeMX иногда
  предлагает `CIRCULAR` по умолчанию — проверять при регенерации `.ioc`.
- **Не потокобезопасен относительно нескольких вызывающих одной шины
  параллельно** (не путать с безопасностью относительно завершения по
  ISR — она обеспечена). Под RTOS с несколькими задачами на одной шине
  сверху понадобится мьютекс.
- **Заголовок `i2c_driver.h` не должен включать `timer.h`.** Раньше
  включал — `time.h` (совпадало по имени со стандартным `<time.h>`,
  тоже пришлось переименовать) объявлял `delay_us(const i2c_bus_t*, ...)`,
  а `i2c_bus_t` в этот момент ещё не был определён (циклическое
  включение через guard). Правило на будущее: заголовок подключает то,
  что нужно ЕМУ САМОМУ для его же объявлений; то, что нужно только `.c`, —
  подключать в `.c` напрямую.
- **`i2c_bus_recovery()`/`is_i2c_bus_stuck()` используют внутреннюю
  подтяжку (`GPIO_PULLUP`).** Слабее внешних резисторов — на шине без
  внешней подтяжки это единственная опора, годится для 100 кГц, но не
  стоит закладываться на неё при повышении скорости шины.
